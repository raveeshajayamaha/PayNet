How PayNet works

Three small ideas from network programming, working together.

1

TCP: a conversation of lines

The core server listens on port 5000. A client opens a socket and sends one text line per command, with fields split by |. The server answers with one line starting with OK or ERR.

> LOGIN|alice|secret
< OK|LOGIN|alice|100000
> TRANSFER|bob|550|lunch
< OK|TRANSFER|17|99450
< EVENT|TX|17|alice|bob|550|...

Each connection gets its own thread, so many users can be served at the same time. The server can also push an EVENT line at any moment, which is why a client needs a separate reader thread.

2

HTTP: the website's language

Browsers cannot open raw TCP sockets, so a second server on port 8080 speaks HTTP and JSON. It serves this page and a small REST API (/api/login, /api/transfer, /api/history ...). After logging in you receive a token that is sent in the Authorization: Bearer header.

Both servers call the very same PaymentService, so there is one set of accounts and one set of rules.

3

SSE: the server talks first

Normal HTTP is request and response. With Server-Sent Events the browser opens /api/stream once and the server keeps the response open, writing a new event: tx message every time you are the sender or receiver of a payment. A ping every 15 seconds keeps the line alive. That is how the history table and your balance update without a refresh.

Why cents?

Computers cannot store 0.1 exactly as a decimal number, so adding money in floating point drifts. PayNet stores every amount as a whole number of cents (12.50 is 1250) and only converts for display. This page does the same conversion before it sends a request.
